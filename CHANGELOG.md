# Changelog

The notes for versions up to 9.3.1 are in [ardalis/Specification's GitHub Releases](https://github.com/ardalis/Specification/releases).

## 10.0.0 (unreleased)

### Breaking changes

#### Ardalis.Specification

- `ISpecification<T>` and `ISpecification<T, TResult>` no longer declare `Query`. `Specification<T>` and `Specification<T, TResult>` keep it. Code that reads `Query` through either interface, or implements it explicitly, no longer builds, with CS1061 or CS0539. Read `Query` through the concrete class instead. A class of your own that implements `ISpecification<T>` can leave `Query` out. An assembly built against 9.x that reads `Query` through an interface throws `MissingMethodException`, so rebuild it. [#36](https://github.com/bandoyer/Specification/pull/36)

#### Ardalis.Specification.EntityFrameworkCore

- `ContextFactoryRepositoryBaseOfT<TEntity, TContext>.AsAsyncEnumerable` calls `CreateDbContext` when an enumeration starts, once per enumeration. In 9.x it called it once, when the method was called. A factory that counts or logs its contexts sees the difference. [#37](https://github.com/bandoyer/Specification/pull/37)
- `ToListAsync` and `ToEnumerableAsync` on a `DbSet<T>` bind an `ISpecification<T, TResult>` to new projection overloads. These apply the specification's `Select` and `PostProcessingAction`, and return `List<TResult>` and `IEnumerable<TResult>`. In 9.x the call bound to the `ISpecification<T>` overload, ignored the `Select` and returned entities. To get entities, pass a specification without a projection. A `Specification<T, TResult>` with no `Select` now throws `SelectorNotFoundException`. [#38](https://github.com/bandoyer/Specification/pull/38)
- With this package's namespace imported, `FirstOrDefaultAsync(default)`, `SingleOrDefaultAsync(default)`, `CountAsync(default)` and `AnyAsync(default)` on a `DbSet<T>` bind to the new specification overloads and throw `ArgumentNullException`. EF Core read `default` as the `CancellationToken`. Leave the argument out, or pass `CancellationToken.None`. With nullable enabled, the compiler reports CS8625 at the call. [#38](https://github.com/bandoyer/Specification/pull/38)
- A `null` argument to `FirstOrDefaultAsync`, `SingleOrDefaultAsync`, `CountAsync` or `AnyAsync` on a `DbSet<T>` throws `ArgumentNullException` for `specification`, where EF Core's own overload threw it for `predicate`. [#38](https://github.com/bandoyer/Specification/pull/38)
- `ContextFactoryRepositoryBaseOfT<TEntity, TContext>.SingleOrDefaultAsync` throws `InvalidOperationException` when more than one row matches, in both overloads, as `RepositoryBase<T>` does. In 9.x it returned the first row EF read. To keep the first row, call `FirstOrDefaultAsync`. [#42](https://github.com/bandoyer/Specification/pull/42)

#### Ardalis.Specification.EntityFramework6

- The provider now has nullable annotations, and its signatures match the EF Core provider's. `RepositoryBase<T>`'s `GetByIdAsync`, `FirstOrDefaultAsync` and `SingleOrDefaultAsync` return `Task<T?>`, or `Task<TResult?>` for a projection, and `GetByIdAsync` requires `TId : notnull`. `WithSpecification` takes an `ISpecificationEvaluator?`, and every other reference-type parameter is non-nullable. With nullable enabled, a caller gets CS8602 where it dereferences one of those results without a null check, CS8625 where it passes `null` for a non-nullable argument, and CS8714 for a nullable `TId`. A subclass that overrides one of those methods gets a nullability warning until its signature matches. The annotations are attributes, so they don't break an assembly built against 9.x, and a project without nullable enabled sees no change. [#21](https://github.com/bandoyer/Specification/pull/21)
- `IncludeEvaluator` no longer applies include strings. A new `IncludeStringEvaluator` does, as in the EF Core provider. A caller that passes `new SpecificationEvaluator(evaluators)` its own list with `IncludeEvaluator.Instance` adds `IncludeStringEvaluator.Instance` before it. Without it, include strings stop loading, with no error. `SpecificationEvaluator.Default`, `RepositoryBase<T>` and `WithSpecification` already use both. [#24](https://github.com/bandoyer/Specification/pull/24)
- `SearchExtension.Search` is removed. Call `ApplyLikesAsOrGroup`, which takes the same argument. [#25](https://github.com/bandoyer/Specification/pull/25)
- The package no longer depends on `Microsoft.CSharp`. A net472 project whose own `dynamic` code got `Microsoft.CSharp` through this package adds its own reference. [#26](https://github.com/bandoyer/Specification/pull/26)
- `IncludeExtensions` is removed, with its `Include<T>` and `ThenInclude<T>` extensions that took an `IncludeExpressionInfo`. To apply a specification's include expressions to a query, call `IncludeEvaluator.Instance.GetQuery`. [#29](https://github.com/bandoyer/Specification/pull/29)
- `IncludeEvaluator.GetQuery` throws `ArgumentException` for an include lambda that isn't a chain of member accesses, such as `x => x.Products.Where(p => p.Id > 10)`, as EF6's own `Include` does. It also throws `ArgumentException` for a `ThenInclude` with no `Include` before it, which only a custom `ISpecification<T>` can hold, where 9.x threw `NullReferenceException`. Write each include as a chain of member accesses. [#29](https://github.com/bandoyer/Specification/pull/29)
- `SpecificationEvaluator.GetQuery` throws `ArgumentNullException` with the `ParamName` `specification` for a null specification, in both overloads, as the EF Core provider does. In 9.x the `ParamName` held the text "Specification is required", and the `Message` changes with it. Only code that reads `ParamName` or `Message` sees a difference. [#32](https://github.com/bandoyer/Specification/pull/32)
- `ToListAsync` and `ToEnumerableAsync` on a `DbSet<T>` bind an `ISpecification<T, TResult>` to new projection overloads. These apply the specification's `Select` and `PostProcessingAction`, and return `List<TResult>` and `IEnumerable<TResult>`. In 9.x the call bound to the `ISpecification<T>` overload, ignored the `Select` and returned entities. To get entities, pass a specification without a projection. A `Specification<T, TResult>` with no `Select` now throws `SelectorNotFoundException`. [#38](https://github.com/bandoyer/Specification/pull/38)
- A `null` argument to `FirstOrDefaultAsync`, `SingleOrDefaultAsync`, `CountAsync` or `AnyAsync` on a `DbSet<T>` throws `ArgumentNullException` for `specification`, where EF6's own overload threw it for `predicate`. [#38](https://github.com/bandoyer/Specification/pull/38)

### Other changes

- Both providers' `DbSetExtensions` have new methods that apply a specification and run the query in one call, so `dbContext.Customers.FirstOrDefaultAsync(spec)` replaces `dbContext.Customers.WithSpecification(spec).FirstOrDefaultAsync()`. The new methods are `FirstOrDefaultAsync`, `SingleOrDefaultAsync`, `CountAsync`, `AnyAsync`, and `AsAsyncEnumerable` in the EF Core provider. `ToListAsync`, `ToEnumerableAsync`, `FirstOrDefaultAsync` and `SingleOrDefaultAsync` also take a projection specification. `CountAsync` and `AnyAsync` evaluate the criteria only, as `RepositoryBase<T>`'s do, so paging doesn't change them. [#38](https://github.com/bandoyer/Specification/pull/38)
- `ContextFactoryRepositoryBaseOfT<TEntity, TContext>.AsAsyncEnumerable` works. In 9.x it disposed its `DbContext` when it returned, so the first `await foreach` threw `ObjectDisposedException`. Each enumeration now opens its own context and disposes it when the enumeration ends, on `break` and on cancellation too. A token passed through `WithCancellation` reaches the query. [#37](https://github.com/bandoyer/Specification/pull/37)
- The EF6 provider's search sends each search term to SQL Server as a parameter, as hand-written EF6 LINQ does. In 9.x it wrote the term into the SQL as a literal. SQL Server now reuses one plan for every term, which can change the performance of a query whose best plan depends on the term. `SearchExtension` adds `ApplySingleLike` and `ApplyLikesAsOrGroup`, and `ParameterReplacerVisitor` is now public, as in the EF Core provider. [#25](https://github.com/bandoyer/Specification/pull/25)
- The EF6 provider's `OrderEvaluator.Evaluate` sorts an in-memory list. In 9.x it threw `RuntimeBinderException` for every specification with an order. `GetQuery` calls `Queryable` through cached delegates in place of `dynamic`, and allocates 128 B to 608 B less per call with an order. [#26](https://github.com/bandoyer/Specification/pull/26)
- The EF6 provider loads every include chain of a specification that has more than one, such as `Include(x => x.Products).ThenInclude(p => p.Images)` and `Include(x => x.Company).ThenInclude(c => c.Country)`. In 9.x it threw `InvalidOperationException` with "A specified Include path is not valid". `IncludeEvaluator.GetQuery` also allocates 296 B to 1400 B less per call. [#29](https://github.com/bandoyer/Specification/pull/29)
